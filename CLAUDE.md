# Archeion

Repository (tracked on GitHub, no secrets or machine config) holding my system-wide point of view: how my projects interact with each other, architecture overviews, and the roadmap. It also has a local web app (backend + frontend) where I view these docs, plans and diagrams, and send prompts, reviews and feedback to Claude.

## Hard rules (never break these)
1. **Tracked on GitHub, so no configuration and no project information in commits.** Anything that names or describes a specific project goes in the gitignored `registry/` folder, never in `docs/`, code, tests or commit messages (ADR 0007). The repo is pushed to GitHub. Claude may add or change the remote and push only when I ask for it. Never commit API keys, tokens, passwords, absolute paths (`<drive>:\...`, `/Users/...`, `/home/...`), email addresses or other personal information, `.env` files, databases or keys. Machine-specific values go in a gitignored `.env`, with a committed `.env.example` holding placeholders. Use paths relative to the repo. `.githooks/pre-commit` (running `.githooks/check-sensitive.ps1`) enforces this. Never skip it (`--no-verify`, `-n`) or change `core.hooksPath`. If it flags a harmless example, put `sensitive-ok` on that line. **Name clashes go to the user** (ADR 0007): when a registered project's name is also an ordinary word already in committed text (a made-up example name in a test, a Mermaid keyword), the hook stops with `REVIEW NEEDED` instead of deciding. Show the user those lines and let them choose: rename, `sensitive-ok`, or approving the term in `registry/reviewed-names.txt`. Never add an approval, or the marker, yourself to get a commit through. See `docs/decisions/0003-track-on-github-keep-configuration-out.md`.
2. **Root helper scripts.** The project root has `setup.bat` (installs the backend venv and frontend node_modules), `configure.bat` (interactive editor for `.env`), `start.bat` (starts backend and frontend, each in its own window), `stop.bat` (stops them by port) and `restart.bat` (runs `stop.ps1`, then `start.ps1`; doesn't start again if the stop failed). They work from any folder (`cd /d "%~dp0"`), and longer logic lives in `scripts/*.ps1`. `start.bat` always starts. On a fresh start the viewer asks for the admin password (ADR 0011). Keep these scripts working whenever the app changes.
3. **Authentication is enforced.** Every backend endpoint requires a logged-in admin session, except `GET /api/health`, `POST /api/auth/login` and first-run setup (`GET`/`POST /api/auth/setup`, which only creates the first password, only while none exists and only when the backend listens on loopback; ADR 0011). The password is stored only as a salted scrypt hash in the backend's SQLite database, never in a file or `.env`. Sessions use an HttpOnly cookie. Changing or resetting the password is done with the CLI (`password set`) and logs out every session. The backend listens on `127.0.0.1` by default. The frontend shows a login page and nothing else until you're logged in. Claude's local access (`/inbox`) goes through the backend's own CLI, not an unauthenticated API.
4. **Backend + frontend.** The viewer is two parts that talk over HTTP: `app/backend/` (API) and `app/frontend/` (UI). The frontend never reads the filesystem directly. It goes through the backend API.
5. **The frontend shows my docs, plans and diagrams**, and the backend serves everything it needs: the doc tree, file content, Mermaid diagrams, roadmap, git history of each doc, and live updates when a file changes. Besides this repo's `docs/`, it serves **read-only** each registered project's `README.md`, `CLAUDE.md`, `CHANGELOG.md`, `ROADMAP.md` and docs folder, and nothing else of it, and it never edits an existing project's files (`docs/decisions/0006-multi-project-registry.md`). The one exception: when the user creates a new project from the viewer, it makes that project's new folder with a `README.md`, a `CLAUDE.md` and optionally a git repository in a root they granted, and never into a folder that exists (`docs/decisions/0028-create-a-project-from-the-viewer.md`).
6. **Feedback loop with Claude.** Prompts, reviews and comments I write in the frontend are stored by the backend and reach Claude. Claude's replies and doc changes show up back in the frontend. Each item targets a project. Items form threads: you reply under Claude's answer, the backend hands Claude the whole conversation, and resolving closes the whole thread (ADR 0018). Each project's session handles its own items (ADR 0006), and this repo's `/inbox` handles every project's items: Archeion's own, and a registered project's by editing that project under its own `CLAUDE.md`, when its `inbox_edits` allows it (ADR 0017). See `docs/decisions/0002-viewer-app-and-claude-feedback-loop.md`.

## Purpose
Sessions here should:
- Build and maintain the system-level picture: what each project is, what it owns, and how they connect.
- Document cross-project interactions: APIs called, data owned, ports, events, dependencies.
- Plan the roadmap: what gets built next, in what order, and why.
- Build and maintain the viewer app in `app/`.

Don't edit sibling projects from this repo, except to carry out a project's inbox item through `/inbox` when its `inbox_edits` allows it (ADR 0017): then read the project's `CLAUDE.md` first, follow it, run its tests, and never commit there. When a sibling project's facts are needed (ports, APIs, stack), read them from that project's `CLAUDE.md`/`docs/` or `../PROJECTS.md`, and record what you learned here with a pointer to the source.

## Stack
- Docs: Markdown, diagrams as Mermaid code blocks.
- Backend (`app/backend/`): Python 3.12, FastAPI, uvicorn, pydantic-settings, watchfiles, stdlib `sqlite3` (no ORM), uv with the environment in `venv/`. SQLite holds the admin credential hash, sessions and feedback. Lint with ruff, test with pytest.
- Frontend (`app/frontend/`): TypeScript, React, Vite, npm, Mantine, React Router, TanStack Query, react-markdown, mermaid, diff2html, React Flow (`@xyflow/react`) with elkjs for the interactive maps (ADR 0015). Lint with oxlint, test with vitest (jsdom).
- Details and reasons are in `docs/decisions/0004-viewer-app-stack-and-layout.md`.
- Version: Semantic Versioning, with `VERSION` as the single source (`docs/decisions/0005-semantic-versioning.md`). Bump it with `scripts/bump-version.ps1 -Part major|minor|patch` and record every change in `CHANGELOG.md` (under `## [Unreleased]` until a release).

## Ports
- Backend: **20300** (AI / Agent APIs range, because it drives Claude), set by `ARCHEION_PORT`.
- Frontend dev server: **20301**, set by `ARCHEION_FRONTEND_PORT`.

## Environment
- Docs: none.
- Backend: `app/backend/venv/`, created by `uv sync` with `UV_PROJECT_ENVIRONMENT=venv`. Database at `app/backend/data/archeion.db` (gitignored).
- Frontend: `app/frontend/node_modules/`, created by `npm ci` (`setup.bat` does both installs).
- Config: the repo-root `.env` (gitignored, `ARCHEION_*` variables). Both the backend and Vite read it. Every setting is defined once in `scripts/settings.schema.json`: `configure.bat` prompts for and validates each one, writes `.env`, and regenerates `.env.example` from the schema (so never edit `.env.example` by hand). To add a setting, add a schema entry, plus a field in `app/backend/app/config.py` if the backend reads it. `tests/test_settings_schema.py` fails if the two drift.
- All of these must be listed in `.gitignore`.

## Commands
- Install: `setup.bat`. Change settings: `configure.bat`. Run: `start.bat`, then open the frontend at port 20301 (the first time, it asks you to create the admin password). Reset the password: `scripts/archeion.ps1 password set`. Stop: `stop.bat`. Restart: `restart.bat`.
- Backend (from `app/backend/`, with `UV_PROJECT_ENVIRONMENT=venv` set): `uv run pytest`, `uv run ruff check .`, `uv run ruff format --check .`.
- Frontend (from `app/frontend/`): `npm test`, `npm run lint`, `npm run typecheck`, `npm run build`.
- Backend CLI (from the root): `powershell -NoProfile -ExecutionPolicy Bypass -File scripts/archeion.ps1 <serve|password ...|inbox ...|projects ...|study ...|design ...|glossary ...|version>`.
- Versions: the app with `scripts/bump-version.ps1 -Part major|minor|patch`, the plugin with `-Target plugin -Part ...`. They're independent (ADR 0005, ADR 0009).
- Feedback: `/inbox` (project skill in `.claude/skills/inbox/`) works through what was written in the viewer.
- Designs: `/design <project>` (project skill in `.claude/skills/design/`, ADR 0022) designs and plans a registered project and keeps it in `registry/designs/`. From the viewer it's a conversation in a thread, like a study. CLI: `design preflight|context|init|show|list|validate|save|stage|approve|handoff|package|consumed|discard`. A project consumes a handed-off design with `/archeion:consume-design` (plugin).
- Code studies: `/study <project>` (project skill in `.claude/skills/study/`, ADR 0019) reads a project's code read-only and saves a snapshot. From the viewer it's a conversation in a thread (ADR 0020), carried between rounds by a draft. CLI: `study scan|list|show|changes|validate|save [--from-draft]|draft save|show|discard`.
- Reports: `/report <project>` (deterministic, project skill in `.claude/skills/report/`) and `/report-guided <project>` (Claude plans it from a prompt, `.claude/skills/report-guided/`, ADR 0025) make a PDF of a registered project. In the viewer: the project page's **Report** button (**Standard** or **Guided**) and **Reports** tab. CLI: `report preflight|catalog|default|validate|read|build|list|verify`, `report preset list|show|save|delete`, `report plan save|show|discard|approve`. Building needs the viewer's frontend running (`start.bat`) and Edge.
- Docs: before finishing, check that relative links between docs resolve.

## Architecture
- `registry/` (**gitignored, private**; ADR 0007): the system point of view. It holds `overview.md` (the big picture), `projects/<project>.md` (one page per project or module: structural facts in YAML frontmatter, cross-project notes in the body; format in `projects/README.md`), `groups/<group>.md` (one page per system of related projects) and `interactions/` (notable cross-project flows). The maps are generated from the frontmatter, not drawn by hand. The viewer shows the folder as the `registry` source.
- `registry.example/` (committed): the empty template `setup.bat` copies to `registry/`. Keep it generic. Only `example-*` names, never a real project.
- `docs/roadmap/`: `roadmap.md` (now / next / later) plus dated plans for larger initiatives.
- `demo-example-data/` (committed, ADR 0030): a made-up project, Example-Project, with its registry data (`registry/`) and its own docs (`example-project/`). The viewer reads it in place (never copied into `registry/`, never in the user's project lists), lists it as **Demo** in the sidebar, below the Projects section, and nothing about it is written or reaches a database or Claude (`services/demo.py`: `read_only`, and the feedback service refuses it). Keep it generic.
- `docs/decisions/`: architecture decisions as `NNNN-title.md` (ADRs).
- `docs/notes/`: session handoffs.
- `docs/updates/`: one short how-to-update note per release that asks the user to do something, `update-vX.Y.Z.md` (format and template in its README). Write it after `scripts/bump-version.ps1`, so it names the right versions, and add a row to the table in its README.
- `docs/guides/claude-cli.md`: the terminal workflow, shown in the viewer's Claude CLI panel (`app/frontend/src/layout/GuidePanel.tsx`). Update it whenever a skill, plugin skill or CLI command is added, renamed or removed. `docs/guides/use-cases.md` (the Use cases page in the sidebar) walks through whole jobs; keep its **(planned)** markers in step with what's actually built. `docs/guides/diagrams.md` says how to write diagrams (Mermaid with the ELK layout and the `logos:`/`mdi:` icon packs, ADR 0014); keep it in step with what `MermaidBlock.tsx` registers.
- `app/backend/app/`: `main.py` (app factory, Origin guard, error mapping, routers behind the session dependency), `config.py`, `db.py` (pragmas, `BEGIN IMMEDIATE`, migrations by `PRAGMA user_version`), `security.py` (scrypt, sessions, rate limit), `paths.py` (the one doc-path check every route uses), `routers/`, `services/` (`docs_fs`, `git`, `events`, `feedback`), `__main__.py` (CLI).
- `app/frontend/src/`: `api/` (fetch client, typed queries), `auth/`, `layout/` (shell, doc tree, feedback badge), `docs/` (Markdown, Mermaid, comment anchors, history and diffs), `feedback/`, `pages/` (home, roadmap, diagrams, search, updates: the notes of `docs/updates/` by target version, from the file names `update-vX.Y.Z.md`), `events/` (SSE → query invalidation).
- `app/backend/app/services/registry.py` (registry pages, checks, discovery), `roots.py` (the named roots from `ARCHEION_ROOTS`, ADR 0008) and `sources.py` (doc sources: `archeion` plus one read-only source per registered project, with its file allowlist). Every docs route takes `source` (default `archeion`).
- `app/backend/app/routers/manage.py` (ADR 0010): the Settings page's API. The backend's only file writes: the `ARCHEION_ROOTS` line of `.env` (`roots.py: write_env_roots`, keeps `.env.bak`), new pages in `registry/projects/` (`registry.py: register`, create-only, only for folders discovery found) the `type:` and `inbox_edits:` lines of an existing page there (`registry.py: set_type`, `set_inbox_edits`, ADR 0016, ADR 0017) and the move of a removed project's page to `registry/removed/` (`registry.py: unregister`, ADR 0026; the loader only reads `projects/`, so it's recoverable; `restore` moves it back, and `purge` is the one place the backend deletes registry data, only for a removed name and after the viewer asks). Never an existing project's files (the one exception is `services/scaffold.py`, ADR 0028: a new project's folder with its README.md and CLAUDE.md, create-only), never anything else in an existing page. The one other writer of a registry page's lines is a user-approved design (`routers/designs.py`, ADR 0022): `ports`, `depends_on`, `group`, `kind` and `status` only.
- `app/backend/app/services/runner.py` + `routers/runner.py` (ADR 0013): the inbox terminal, `claude "/loop <interval> /inbox"` in its own console window, started and stopped from the Settings page (`app/frontend/src/runner/`). It's tracked by PID plus process start time in the `runner` table, and starting it needs a loopback backend. `start.bat`/`stop.bat` don't touch it.
- `app/backend/app/services/responder.py` + `routers/responder.py` (ADR 0020): on-demand Claude. When switched on (Settings), the backend's `watch_responder` task starts a run whenever a feedback message newer than the last run's id watermark is open: by default a visible session (`cmd /c claude "/inbox"` in its own window, closed by the backend once the Stop hook `scripts/on-demand-done.ps1` writes the run's marker), or with Headless a `claude -p` run with no window, logged as stream-json to `app/backend/data/responder/` (ADR 0021). Edits accepted, Archeion's CLI allowed, `--add-dir` per granted root and, unless switched off in Settings, per project or module with a waiting item. Each run is a `claude_jobs` row. Max Claude instances (1 or 2, default 1) counts the inbox terminal and every run; with 1 the terminal and on-demand Claude exclude each other. These, the inbox terminal, git and headless Edge (for the length of a report build, ADR 0025) are the backend's only processes.
- `app/frontend/src/graph/` (ADR 0015): `GraphView`, the interactive nested graph (React Flow, ELK in a web worker, lazy-loaded through `LazyGraph`), and `graph.ts`, its pure fold/layout helpers. Every map uses it, with the Mermaid version behind a toggle.
- `app/frontend/src/projects/`: projects overview, group and project pages, and `map.ts`, which generates the maps from the registry (`buildGraph` for GraphView, `buildMermaid` for the Mermaid toggle). `docs/links.ts` resolves links across sources.
- Live updates: watchfiles (project roots without recursion, docs folders with recursion, restarted when the registry changes) and a `PRAGMA data_version` check on the feedback table publish to an in-process bus, which `GET /api/events` streams over SSE.
- Designs (ADR 0022): `registry/designs/<project>/<slug>/` holds the working copy (`brief.md`, `architecture.md`, `plan.md`, `questions.md`, `decisions/`, `model.json` in the study schema plus a `structure` block, a generated `design.md` and `info.json`) and, once approved, immutable `revisions/<date>-rN/`. `services/designs.py` is the only writer (validation, atomic replace, approve, package, preflight), `services/design_checks.py` the read-only impact list and built-vs-designed comparison, `routers/designs.py` the API (`/api/designs`) behind the project page's **Design** tab (`app/frontend/src/design/`). Approving also writes the structural lines (`ports`, `depends_on`, `group`, `kind`, `status`) of the project's registry page (`registry.py: plan_structure`, `apply_structure`, only when the user approves, only those keys). A handoff is a thread for Archeion (`anchor.task = handoff-design`), and `design package` is the only place a design is written outside the registry: a plain copy into the project's `.archeion/designs/<slug>/`, only when `inbox_edits` allows it. Everything is private (ADR 0007).
- Interactive study views (ADR 0024): `study/ViewSwitch.tsx` puts an **Interactive / Mermaid** switch on every study and design diagram (remembered in `localStorage`). Flows are drawn by `study/SequenceView.tsx` (layout in `study/sequence.ts`, zoom and pan in `docs/PanZoom.tsx`), logic and states by `GraphView` (`study/graph.ts`: `activityGraph`, `stateGraph`), and a click opens a side panel (`ComponentDetails`, `study/NodeDetails.tsx`) through the `node` URL parameter instead of leaving the diagram. `docs/DiagramFrame.tsx` adds wheel zoom, a Find box and hover highlights to Mermaid output (`docs/diagramLabels.ts`, `global.css`). `GraphView` draws ELK's routed edges and has a Find box. `study validate` warns about a component level wider than 12.
- Reports (ADR 0025): `services/reports.py` (the section catalog, presets, the guided plan draft and `content()`, which resolves a preset into what the print page draws) and `services/report_render.py` (headless Edge over the DevTools protocol, the build, `verify`, `ReportJobs`) are the only writers of `registry/reports/<project>/` (`presets.json`, `plan.json`, and each PDF with a `.json` build record). `routers/reports.py` is the API (`/api/reports/{project}/...`). The frontend's `report/` folder has `PrintReport.tsx` (the print page at `/print/report/:project`, outside the shell, always light, one section per page, `document.body.dataset.reportState` says when it's drawn), `sections.ts` (diagram code from the study model, `@page` rules), `ReportDialog.tsx` (Standard), `GuidedReport.tsx` (Guided), `ReportTab.tsx` and `SortableSections.tsx` (`@dnd-kit`). `docs/PrintContext.ts` makes `MermaidBlock` draw plain light SVG and decides which diagrams get a landscape page. The build prints with a session of its own that it deletes afterwards, so no endpoint is public that wasn't. Everything is private (ADR 0007).
- Glossaries (ADR 0023): `registry/glossary/<project>.json` holds a project's terms. `services/glossary.py` is the only writer (validated, atomic), `routers/glossary.py` the API (`/api/glossary`), `src/glossary/` the project page's **Glossary** tab. CLI: `glossary list|set|remove`.
- Code studies (ADR 0019): `registry/studies/<project>/<YYYY-MM-DD>-<commit7>/` holds `study.json` (the model, validated by `services/studies.py`) and `notes.md`. Snapshots are immutable, written only by `study save`, and pruned beyond `ARCHEION_STUDY_KEEP`. `services/study_scan.py` is the read-only code inventory, `routers/studies.py` the read API (`/api/studies`, `/api/studies/search`, `/api/system/links`, which also reports drift against `depends_on`). The frontend's `src/study/` generates every study diagram from the model (`mermaid.ts`), so never hand-draw them in a snapshot.
- `.claude-plugin/marketplace.json` + `plugins/archeion/` (ADR 0009): the plugin for sessions in registered projects (`/archeion:inbox`, `context`, `ports`, `notify`, `consume-design`, `design-consumed`, a SessionStart hook), installed by the user at user scope. `plugins/archeion/scripts/archeion.ps1` finds Archeion and checks its minimum version (`$MinArcheion`). It has its own SemVer and changelog. Never copy its skills into projects.
- `.githooks/pre-commit` runs `check-sensitive.ps1` (blocks commits with secrets, absolute paths or personal info) and `check-plugin-version.ps1` (blocks plugin changes without a plugin version change). Activated with `git config core.hooksPath .githooks`. Scan everything by hand with `powershell -NoProfile -ExecutionPolicy Bypass -File .githooks/check-sensitive.ps1 -All`.
- `setup.bat`, `configure.bat`, `start.bat`, `stop.bat`, `restart.bat` (root) and `scripts/` (`common.ps1`, `setup.ps1`, `configure.ps1`, `settings.schema.json`, `start.ps1`, `stop.ps1`, `send-ctrl-c.ps1`, `archeion.ps1`, `inbox-count.ps1`, `bump-version.ps1`).
- `.claude/settings.json` runs `scripts/inbox-count.ps1` as a SessionStart hook, which announces open feedback, and `scripts/on-demand-done.ps1` as a Stop hook, which only acts in on-demand sessions (ADR 0021).

## Conventions
- One fact lives in one place; link to it rather than copying it.
- A **project** has its own git repository, and a **module** is a part of one, inside its repository (ADR 0016). `type:` on a registry page overrides detection; set it with `projects type <name> project|module|auto` or from the viewer. A project's inbox includes its modules' items.
- `inbox_edits:` on a registry page says whether Archeion's `/inbox` may edit that project (ADR 0017): allowed when left out, and a module follows its project. New pages for projects get `inbox_edits: true`. Switch it with `projects inbox-edits <name> on|off|auto` or on the project page.
- A **study** is a generated, dated snapshot of a project's internals, kept only in the private `registry/` (ADR 0019 amends "facts stay in their home" for studies only). Never edit a snapshot; study again.
- Each registry page records `verified:` (the date its frontmatter was last checked against the real project). Facts that belong to a project (endpoints, commands, internals) stay in that project's own docs, which the viewer shows live. Link to them, don't copy them.
- New projects: the viewer's Settings page (roots and a Register button per folder), or `scripts/archeion.ps1 projects scan` (dry run), then `--write` for stub pages. `projects list` shows the tree and problems.
- Use the workspace port ranges and database rules (`../CLAUDE.md`) as the baseline when describing or planning services.
- Roadmap items use absolute dates, never "next week".
- When starting a session, check for open feedback from the frontend (see ADR 0002) before other work: `inbox list --project archeion`.

## Gotchas
- A report build prints the frontend's print page, so `report build` and the dialog's Generate need the frontend running (`start.bat`), and Edge (`ARCHEION_REPORT_BROWSER` if it isn't found). `report preflight` says which is missing.
- Example text in skills and docs must stay generic: the commit hook blocks the name of a registered project even in an example (ADR 0007).
- `core.hooksPath` lives in `.git/config`, which isn't versioned. After every fresh clone, run `git config core.hooksPath .githooks`, or the sensitive-content check won't run.
- The check also runs on docs: describe other projects by repo-relative path (`../<project>`), never by drive path. It also blocks the names of registered projects and workspace folders in committed text, using names it reads from the private `registry/` at commit time (ADR 0007).
- The check also runs on code. A line like `token = something_long` or `password: some.value` trips its secret pattern even when nothing secret is in it. Name such variables `raw`, `pw`, `secret` and so on, and generate test passwords at runtime (`tests/conftest.py: make_pw`). <!-- sensitive-ok: example of what trips the check -->
- `.claude/settings.json` denies reading `.env.*`, and that covers `.env.example` too, so Claude can't write it. It's generated anyway: change `scripts/settings.schema.json`, then run `configure.bat` (or `scripts\configure.ps1 -ExampleOnly`).
- FastAPI 0.163 keeps included routers as `_IncludedRouter` objects, so `app.routes` isn't flat. `tests/test_auth_required.py` walks `app.openapi()["paths"]` instead.
- Project sources are read at runtime from the named roots in `ARCHEION_ROOTS` (ADR 0008) and, if set, `ARCHEION_WORKSPACE_ROOT` (empty by default: nothing is granted until a root is added, ADR 0012). Tests set `workspace_root=".."` themselves. Registry `path`s must be relative and stay inside their root: relative to this repo without `root:`, relative to the root with it. The commit hook doesn't read `.env`; it blocks registered projects' names whatever their root. Nothing from a project is ever copied into this repo, which is what keeps publishing Archeion from publishing the projects.
- `inbox --here` needs the caller's folder. `scripts/archeion.ps1` passes it as `ARCHEION_CALLER_DIR`, because the CLI itself runs from `app/backend/`.
- The SessionStart hook uses a relative path (`scripts/inbox-count.ps1`), so it only fires when Claude Code starts at the repo root.
- Claude Code runs the Archeion plugin from a cached copy per version, so an edit under `plugins/archeion/` reaches project sessions only after a plugin version bump, `/plugin marketplace update archeion` and a plugin update. The plugin is turned off in this repo, so test it from a registered project's session.
- uv only reads `UV_PROJECT_ENVIRONMENT` from the environment. Set it to `venv` before any `uv` command in `app/backend/`, or uv creates a second `.venv/`.
