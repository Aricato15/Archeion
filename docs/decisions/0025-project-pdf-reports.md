- Plan: [project PDF reports](../roadmap/2026-11-17-project-report-plan.md)

## Context
A project's facts are spread over the registry page, its docs, a study, a design and a glossary. There was no way to hand someone one document that holds all of it, with the diagrams. Reading it in the viewer works for me, not for someone who has no access to it.

## Decision
1. **A report is a PDF built from a section catalog.** `report catalog` lists what exists for a project: overview, the project's docs, the study (component map, flows, activities, data, states, interfaces, findings, notes), the design, the glossary and the project's place in its group. A section with no source is listed as unavailable with the reason, never silently dropped.
2. **The reader chooses and orders the sections** in a dialog on the project page (a checkbox per section and per sub-system diagram, drag or use the keyboard to reorder, page options). A choice is saved as a named **preset** per project, in the private registry.
3. **Diagrams are vector and complete.** The component map is drawn compact (the top level), and every sub-system (a component with children) is drawn as its own diagram, one level each, with what it reaches outside as dashed ghosts. Flows, logic, states and the schema are drawn in full. They are generated from the same study model and the same Mermaid generators the viewer uses, so a report and the viewer can't disagree. A diagram that would be unreadable on a portrait page (a wide map, a flow with many lanes) gets a landscape page of its own, chosen by whichever orientation shrinks it less.
4. **Rendering is a print route plus headless Edge.** The frontend has a print-only route (`/print/report/:project?preset=<name>`) that lays out the sections as static HTML and SVG, always in the light theme, one section per page. The backend turns it into a PDF with headless Edge (no new dependency on Windows 11), driven over the DevTools protocol with the `websockets` package that uvicorn already needs. The page says when every diagram is drawn (`document.body.dataset.reportState`), and the PDF is printed with page numbers in the footer. This adds one process to the list in ADR 0013 and ADR 0020 (the inbox terminal, on-demand Claude, git): **headless Edge, for the length of a build.**
   - **No new way in.** The renderer gets a session of its own, created in the database for the build and deleted when it ends (also when it fails), and sets it as a cookie through the protocol. No endpoint is public that wasn't, so the login requirement stays whole.
   - **No frames.** A report is shown by opening the PDF in its own browser tab. Nothing is framed, and `X-Frame-Options: DENY` stays on every response.
   - The PDF is printed from the viewer's **frontend**, so building needs it running (`start.bat`). `report preflight` and the dialog say so, and say when Edge isn't found (`ARCHEION_REPORT_BROWSER`).
   - A build from the viewer runs in a background thread, one at a time, and is polled by id.
5. **Two ways to make a report, with two skills and two UI options**, both ending in the same build:
   - **Standard** (`/report <project>`): deterministic. The reader picks and orders sections, and the PDF is built from the registry, the project's docs and the model. No prompt and no Claude, so the same choices give the same PDF. The skill is a thin wrapper around `report preflight`, `build` and `verify`, and the dialog's **Generate PDF** needs no Claude session.
   - **Guided** (`/report-guided <project>`): the reader gives a prompt (audience, purpose, emphasis) and may give a desired structure (an outline in their own words). Claude reads the catalog and the sources (`report read`) and saves a **report plan** as a draft (`report plan save`): an ordered list of **sourced** sections (catalog sections, shown verbatim) and **authored** sections (Claude's text). It starts as a thread anchored to a `report` task, like a study (ADR 0020). The reader reorders or drops sections in the viewer, may ask for changes in the thread, and presses **Approve and build**, which turns the plan into a saved preset and builds it. The same section checklist as the standard report appears twice: before asking, to scope which sections Claude may read, plan and cite (the request carries the list), and in the plan review, to add or remove sourced sections. Claude doesn't approve or build unless asked to.
6. **What Claude writes is labeled and cited.** Every authored section carries a "Written by Claude" label in the PDF and a Sources line, and `report plan save` refuses an authored section that cites no available catalog section. A guided report normally opens with an executive summary. Sourced sections are never rewritten. A standard report has nothing written by Claude.
7. **Reports are private** (ADR 0007). Presets, the plan draft and the PDFs (with a build record beside each) are written only by `services/reports.py` and `services/report_render.py`, to `registry/reports/<project>/`, which is gitignored. A report is never copied into a project and never committed.

## Consequences
- Headless Edge must exist, and the frontend must be running, for a build. Both are checked up front, with the fix named.
- The print route is a second place that draws the study diagrams (through the same generators), so a new diagram kind needs adding to `report/sections.ts` as well as to the viewer.
- A report is as fresh as its study and design. The skills offer `/study --refresh` when the study is behind. A preset keeps sections as ids, so a rebuild picks up a newer study; Claude's authored text does not update itself.
- A very wide flow (many lanes) is still small even on a landscape page. That is the limit of fitting it on A4 or Letter.
- The guided plan draft is polled by the viewer every few seconds, as it is written by another process (Claude's CLI), rather than pushed over the event stream.
- A project whose registry page has only the template's placeholder paragraph shows that paragraph as the cover's subtitle: it is the page's own summary.
