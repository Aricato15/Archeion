# 0022: Design and plan a project from Archeion

- Status: Proposed (2026-11-17)
- Date: 2026-11-17
- Builds on: [ADR 0006](0006-multi-project-registry.md), [ADR 0007](0007-keep-project-information-out-of-the-repo.md), [ADR 0017](0017-inbox-may-edit-registered-projects.md), [ADR 0018](0018-feedback-threads.md), [ADR 0019](0019-code-studies.md), [ADR 0020](0020-study-conversations-and-on-demand-claude.md)
- Replaces: the planned `/brainstorm` skill and the planned `/archeion:bootstrap` in [use case 3](../guides/use-cases.md).
- Amends: [ADR 0017](0017-inbox-may-edit-registered-projects.md), see Amends below.

## Context
A project often begins outside Archeion: an empty folder, or an existing one with a `CLAUDE.md` that only names the tech stack. It gets registered, and then the real thinking starts: what the project is for, how it should be built, how it fits the other projects, and in what order to build it. Today that thinking happens either in the project's own session, where Claude can't see the rest of the system, or as free-form chat in Archeion's session, where the result has nowhere to live except a registry page body.

Archeion already has the pieces such a job needs: the system picture (registry, groups, maps), what other projects expose (studies and `/api/system/links`), generated diagrams, reviews and comments on any doc, threads with a draft carried between rounds (ADR 0020), and a way to put work into a project's inbox (ADR 0017). What's missing is a place where a design is a first-class thing: it has stages, it's reviewed, it's approved, and it's handed to the project to build.

## Decision
1. **A design is a living document set per project, kept in the private registry.** `registry/designs/<project>/<slug>/` holds `design.md` (frontmatter: `stage`, `updated`, `revision`), `brief.md` (purpose, users, scope, non-goals), `architecture.md` (Mermaid diagrams, ADR 0014), `plan.md` (phases with absolute dates, never "next week"), `questions.md` (what's still open) and `decisions/NNNN-*.md` (the project's own decisions, written in the shape of an ADR). The slug defaults to `main`; a second slug lets an existing project get a design for one feature without touching the first. Everything is in `registry/`, so no project information reaches a commit (ADR 0007), and the viewer already shows the folder as the `registry` source, with comment anchors, reviews and history.
2. **The intended system is a model, like a study.** Next to the prose, `model.json` uses the study schema (ADR 0019) for what is *intended*: components, interfaces it exposes and calls, entities, flows, states, plus the structural facts that go into the registry page (ports, `depends_on`, group, kind). The viewer draws the diagrams from it with the same generators as studies, so a design's diagrams can't drift from its model, and a later study of the built project can be compared with the design (point 8). Prose may embed hand-written Mermaid for anything the model doesn't cover.
3. **Stages, with the user in charge of each move.** `brief` → `architecture` → `plan` → `approved`, then `handed off` once the project has consumed it. Claude proposes and revises. Only the user moves a design to the next stage or approves it, in the viewer or in the thread. Going back is allowed.
4. **Designing is a conversation, as studying is.** **Ask Claude to design** on the project page's **Design** tab starts a thread for Archeion, anchored to the task (`anchor.task = {type: "design", project, slug}`), answered by `/design <project>` (a skill in Archeion's own session) through `/inbox` or on-demand Claude (ADR 0020). Each round Claude reports what it changed, asks what it needs, and keeps a draft the Design tab shows with diagrams. The user also reviews and comments on any design doc like any other doc, and those comments land in the same inbox.
5. **Claude designs with the system in view.** `design context <project>` (CLI, read-only) hands Claude one bundle: the project's own `CLAUDE.md` and docs (tech stack and rules), the registry overview, its group and every neighbour's page, the latest study's exposed interfaces for each neighbour, ports already taken, `/api/system/links` drift, and the workspace rules (port ranges, one SQLite database per service). When the project already has code, a `/study` comes first, and the design is written as a change on top of what's built.
6. **The backend is the only writer of designs**, as for studies (ADR 0019 point 3). `design save` validates the model (every reference names an element, ports fall in the workspace ranges and aren't taken, `depends_on` names registered projects), keeps one draft, and allocates revisions. Claude never writes into `registry/designs/` directly.
7. **Approving freezes a revision and updates the registry.** `design approve` copies the design to `revisions/<date>-r<N>/` (immutable, like a study snapshot) and, after confirmation, writes the structural facts into the project's registry page: `status: planned`, ports, `depends_on`, group. Nothing else in the page changes, and `verified` is left alone until a study checks the built result.
8. **Handoff is a package the project consumes.** Archeion doesn't write a design into the project's docs. It delivers a **design package**, and the project's own session turns it into the project's docs with its own skill, `/archeion:consume-design` (a new plugin skill), which knows the project's `CLAUDE.md` and conventions better than Archeion's session does.
   - **The package** is `.archeion/designs/<slug>/` in the project's folder: the approved revision's `brief.md`, `architecture.md`, `plan.md`, `decisions/`, `model.json`, and `handoff.json` (slug, revision, date, the handoff thread's id). It holds only this project's own design and its direct interfaces, never the registry overview or other projects' pages, because the project's repository may be pushed. `.archeion/` is a namespace, so later features don't need another dot folder.
   - **Delivery** is a step on Archeion's side, done by the `/design` skill. `design handoff <project>` creates a thread targeted at the project, `anchor.task = {type: "handoff-design", project, slug, revision}`, and Archeion's `/inbox` carries it out by copying the package into the project, a plain copy with no interpretation, then replying with the files. It needs the project's folder on this machine and `inbox_edits` allowing it (ADR 0017); the skill checks both before it starts (point 11) and says what's missing instead of failing halfway.
   - **Consuming.** `/archeion:consume-design [slug]` first looks for a package in `.archeion/designs/`. **If there's none, it says so and stops, changing nothing.** It never fetches a design from Archeion itself, so what it consumes is always what was delivered. With a package, it reads it and the project's `CLAUDE.md`, shows what it will write and asks, then: writes the design where the project keeps its docs (its `CLAUDE.md` says, else `docs/`), the decisions as ADRs with the next free numbers (`docs/decisions/`), the plan into `ROADMAP.md`, and additions to `CLAUDE.md` for the stack, ports and conventions. It runs the project's checks, never commits, removes the package's copied content, leaves a short `receipt.md` (revision, date, files written) in the folder, and replies on the handoff thread, which marks the design `handed off`. It then offers to start the first phase of the plan. A later revision is consumed the same way, as a change against the receipt. Running it again with no new package does nothing.
   - **After the handoff** the project's own docs own the facts (the convention in `CLAUDE.md`: link, don't copy). The registry keeps the revision as history, and the page body shrinks to cross-project notes. Whether to commit or ignore `.archeion/` is the project's choice; the package is transient and the receipt is small.
9. **Building feeds back.** `/archeion:report` and `/archeion:inbox` can cite a revision when the build departs from it, and Archeion's side opens a thread on the design (a deviation, an open question, a change request) instead of letting the design go silently stale. A later `/study` of the project is compared with the approved model, and the differences show on the Design tab as **built vs designed**.
10. **Cross-project effects are surfaced, not applied.** If a design calls an endpoint a neighbour doesn't expose, or changes a port or contract another project uses, the Design tab lists it, and the user can send an item to that neighbour's inbox with one click. Archeion never edits the neighbour as a side effect of designing.
11. **Skills own the setup.** The user shouldn't have to visit Settings or run CLI commands to get a design going. Each skill checks what it needs before it starts and either fixes it, after asking, or says exactly what's missing and stops. `/design` checks that the project is registered (offers `projects scan --write --only <name>`), that its folder is reachable under a granted root (otherwise says to add the root on the Settings page, the one thing it can't do), that a study exists when the project has code (offers `/study`), and, when handing off, that `inbox_edits` allows it (offers `projects inbox-edits <name> on`). `/archeion:consume-design` checks for the package and the project's `CLAUDE.md`, and stops quietly when there's no package. Neither skill assumes anything the CLI can tell it (`inbox show` and `design context` report what's configured).

## Settled questions (2026-11-17)
- **One design or several per project?** Several, by slug, from the start. A new feature on a mature project is the same job on a smaller scale.
- **Does an empty project need `CLAUDE.md` first?** No. `design context` reports its absence and the design asks for the stack instead. A project that has one keeps it as the source for stack and conventions, and consuming a design may add to it.
- **How does a design reach the project?** As a package in `.archeion/designs/<slug>/`, delivered by Archeion and consumed by the project's own skill, which does nothing when no package is there (point 8). The skill is named `consume-design` rather than `implement-design` because it turns the package into the project's docs, and building is the step after. Other names considered: `/archeion:handoff` (suggests the sending side) and `/archeion:bootstrap` (wrong for a project that already has code).

## Amends
[ADR 0017](0017-inbox-may-edit-registered-projects.md) said nothing is added to the projects' own repositories, so they never have to name Archeion. A handoff adds `.archeion/` to the project, with a transient package and a receipt, so a project that has been handed a design names Archeion in that folder. It's still the project's repository and the project's choice to commit it.

## Consequences
- The project page gets a **Design** tab (stage, draft, brief, architecture, plan, decisions, questions, diagrams, revisions, handoff status), and the Projects page shows each project's design stage.
- New backend pieces: `services/designs.py`, `routers/designs.py`, a `design` CLI group, a `/design` skill, a migration only if design runs need rows of their own (draft and revisions live on disk, like studies). New plugin skill `/archeion:consume-design` means a plugin minor version bump and a new `$MinArcheion`.
- `registry.example/` gets a generic `designs/` template (`example-*` names only).
- The CLI guide and the use cases page change in the same release as each phase (the planned markers in [use case 4](../guides/use-cases.md) follow what's built).
- A design is private by construction, but a handoff puts a design's content into a project's own repository, which that project may push. That is deliberate, and it's the user's repository. The package is limited to the project's own design, and it never reaches Archeion's repository.
- The design's stages become `brief`, `architecture`, `plan`, `approved` and `handed off`.
- The study and design models share a schema, so a change to one needs a schema version check against the other.
